1. 目标与一期范围

核心判断：“宠物种类少”只是表面问题；孩子今天喂养的宠物能否在明天的故事里被认出来、保持性格并留下共同经历，才决定它能否成为长期情感资产。本期同时完成身份统一和最小故事闭环，不等养成做完后再另起一个临时角色系统。

产品目标

提升首次领养完成率、打卡后喂养率、同一孩子档案的回访率，以及领养后故事创作率。宠物陪伴应让故事与日常习惯相互带动，而不新增签到压力。

一期用户价值

孩子能选一只喜欢的宠物、给它命名、喂养并看到成长；再次创作故事时，系统会自然带入“我的这只宠物”，不是重新挑选。0–2 岁需共同操作，不要求独立识字。

新档案：建立孩子档案 → 选宠物 → 命名与欢迎 → 完成第一次打卡 → 领取食物卡 → 首次喂养 → 宠物正式入住 已有档案：选择该孩子 → 一次性领养 / 确认旧宠物 → 保留已有养成资产 → 继续打卡与创作 创作故事：选择孩子档案 → 展示不可在此更换的宠物卡 → 服务端带入宠物快照和安全经历 → 生成故事

2. 从“伙伴”到“主宠物”

2.1 统一产品身份

  • 孩子档案下只有 1 只主宠物。它拥有稳定的物种、名字、角色性格、形象版本、成长阶段和故事经历。不同孩子档案互不共用宠物。
  • “建立档案”“编辑孩子档案”“创作故事”“打卡花园”中涉及本角色的文案统一为“宠物”。创作故事页删除伙伴预设、自定义伙伴和每次重选逻辑，只展示档案绑定宠物的只读提示。更换入口只在孩子档案的“我的宠物”中。
  • 旧的芭比娃娃、奥特曼等未授权第三方角色不得出现在新宠物目录、新档案选择或新故事创作选项；历史故事不强制改写。
  • 宠物是陪伴者，不是“做不好会挨饿”的受害者。漏打卡、不喂养不会掉级、生病、离家或说责备台词。

2.2 首发目录：12 种原创物种

目录以真实宠物乐园里常见且儿童易辨认的物种为灵感，不使用他人作品形象、真实照片或游戏 IP。物种名称是真实动物名称，外观、名字和故事性格由产品原创。动物可在“梦境花园”共同生活；不暗示每一种都适合家庭饲养。

分组petKey / 展示名稳定的故事角色性格（默认，可用安全模板微调）
身边的小朋友cat 小猫、dog 小狗、rabbit 小兔子、hamster 小仓鼠爱观察、热情可靠、温柔敏捷、小心收藏美好。

目录是内容资产集合，不是 12 套独立玩法。每种至少提供统一规格的头像、站立/开心/入睡三态和透明底主形象；成长阶段优先复用通用比例、动作、光效及场景装饰，避免首期产出 12 × 5 套高成本独立美术。目录字段预留 assetVersion、启用状态与排序，新增物种不改历史档案。

食物与动物知识边界：已有“牛奶、蔬菜等”食物卡用于认识儿童饮食中的食物与营养，不等于现实动物的适宜食谱。喂养动效采用“把食物卡变成星光能量送给梦境宠物”的幻想表达，不表现真实动物直接进食卡片食物；卡册和宠物页明确标注“游戏喂养不代表真实动物饮食方法”。故事也不得称某物种可安全食用所有卡片食物。

3. 首次领养：短仪式与明确状态

状态 / 触发用户所见与可操作系统规则
新建档案，未选宠物选 1 只宠物，查看姓名和一句性格介绍；可在目录中来回比较。可先保存孩子资料，但进入打卡养成或故事创作前须完成领养；不随机代选。
提交领养输入 2–12 个字符宠物名，可用默认建议名；看到宠物一句固定欢迎语与轻动效，约 15–30 秒完成。保存宠物目录 key、名字、性格模板、资产版本及档案绑定；一次提交幂等。
已领养，尚无成功喂养宠物显示“刚入住”；可在档案宠物页更换物种与名字。更换物种只替换身份，不产生奖励，不重置已发生的打卡；第一张食物卡尚未消费。
首次成功喂养出现“正式入住”反馈；后续查看成长记录。服务器在第一条成功喂养事件提交时永久锁定物种；即使事后冲正该次喂养，也不解除身份锁定。并发提交仍只能有一只主宠物。改名允许，成长和故事快照不清零。
锁定后不能随意换物种；宠物名可编辑。未来可换同物种外观，但一期不做装扮系统。若需要因误选更换物种，作为客服纠错流程另评估；不得用“删除宠物重新领养”绕过成长记录。

旧档案迁移：旧伙伴为猫、狗、兔且能无歧义识别时，只预选对应宠物供用户确认，不静默领养；其他旧值不映射，显示完整目录。旧养成记录属于孩子档案，领养后继续保留原成长值、已获卡与喂养记录。已有成功喂养的档案在首次确认新宠物后立即锁定物种；确认前要明确提示“领养后此物种将固定”。旧故事保留原内容，不回填新宠物。

未领养时的故事入口：点击“生成故事”先展示领养引导，保留已选孩子档案与已填写的创作信息；领养完成返回并继续。拒绝领养可返回，不后台随机插入宠物，也不以旧 partnerJson 绕过。

4. 升级节奏：共同经历，而非刷数值

保留现有“打卡获卡 → 消费卡喂养 → 增长值 / 营养属性累计”的基础机制；本增量明确宠物阶段、反馈与展示节奏。食物卡和成长值是游戏进度单位，不得标为真实蛋白质克数、维生素摄入量或孩子身高增长。

阶段累计成长值门槛孩子可感知的变化设计意图
1 · 初来乍到0–9记住宠物名字，轻触有眨眼/挥手反馈。领养当天即有归属感。
2 · 熟悉新家10–29增加招呼动作和专属欢迎短句。正常喂养节奏下约第 3–5 天可见第一次升级。
3 · 一起探险30–69增加探索动作与故事里的主动帮助方式。积累一段共同经历，而非一次爆发完成。
4 · 星光搭档70–139花园背景点亮一处共同探索的角落。让长期回访有可见变化。
5 · 长久陪伴140+获得非交易型纪念反馈；继续累计成长，不毕业、不清零。维持可持续关系，不制造终点焦虑。
  • 沿用基础 PRD 的有效喂养增长和每日上限；同一业务日达到上限后，喂养前提示并保留食物卡，不先扣卡。升级按服务端结算的累计成长值判断，不靠客户端动画或连续打卡天数。
  • 以常见“每天两次有效喂养、每次 +2”为示例，阶段 2 约第 3 天、阶段 3 约第 8 天；真实到达时间随选择和上限而变，UI 不承诺具体日期。第一次升级应有清晰的形象/动作变化，不能只有数字跳动。
  • 一次喂养的反馈顺序：卡片化为星光 → 宠物抬头接收 → 成长条上升 → 若跨阶段，触发一次升级演出与短句。单次演出建议 2–4 秒且可跳过；减弱动态效果时用静态过渡。
  • 漏打卡不减成长值；撤销与重复请求按基础 PRD 的可追溯冲正规则执行。已经展示过的最高阶段不回退，纠错仅调整可用成长余额/后续进度，必要时显示“记录已修正”，避免宠物突然变小。
  • 阶段不依赖收集齐所有 6 类营养，避免孩子因偏好某张卡而长时间卡关；营养属性用于食物认知和视觉多样性。若基础 PRD 的旧门槛与本节不一致，以本节为准，需在灰度迁移中保护既有最高阶段。

5. 一期故事联动：让宠物真的“认识我”

5.1 固定角色与最小连续性

  • 创作页选定孩子档案后，展示“今晚，{宠物名}会陪{孩子称呼}进入故事”的宠物小卡。小卡可点开看宠物资料，但不可在创作流程中重选物种；改名跳到“我的宠物”，返回后刷新展示。
  • 服务端根据 childProfileId 读取已绑定主宠物，向故事生成器注入只读快照：petKey、宠物名、稳定性格、当前阶段、形象版本和最多 3 条安全事实。客户端传来的宠物字段不作为事实来源。
  • 每篇新故事必须自然出现该宠物，并保持同一物种和核心性格；角色可随故事主题有新行动，不能随机改成别的动物、他人 IP 或把宠物写成惩罚孩子的监督者。故事失败重试沿用同一宠物快照。
  • 最小共同经历只取可验证事件：已完成的第 N 篇私密故事、最近的官方习惯模板（如“刷牙”）完成次数、一次阶段升级或上篇故事的安全场景标签。没有可用事实就只带宠物身份；不编造“它记得你做过某事”。

5.2 结构化记忆的生成边界

记忆种类一期可注入示例不得注入
共同故事“这是小禾和小芽一起完成的第 8 个睡前故事。”整篇历史故事、公开故事评论、其他孩子档案的故事。
习惯同行“最近一起完成了 3 次刷牙打卡。”自定义习惯原文、撤销的打卡、遗漏天数、好坏评价。
安全场景标签“上一次故事的场景是海底世界。”原始自由输入、健康/疾病/家庭冲突、模型未经审核生成的个人事实。

记忆由成功事件和白名单模板在服务端汇总，按最近优先且去重，最多 3 条；生成故事成功后才递增故事计数。撤销打卡后，下次生成不再引用该事实。存储只需结构化事件引用与枚举标签，不做一期 AI 自由摘要、向量检索或永久“人格记忆”。历史故事保留生成时的宠物快照，不因改名/升级被改写。

情感表达样例：刷牙后是“宠物和孩子一起守护月亮牙齿”；收玩具后是“帮玩具回到星光小屋”；阅读后是“在故事书里找到梦境地图”。故事可以呼应努力，但不说“不做某件事宠物就会伤心/挨饿”。故事生成、阅读与分享都不额外发成长值或积分，不自动点亮“听故事”习惯。

5.3 失败与降级

未领养返回 PET_ADOPTION_REQUIRED 并保留创作草稿；宠物快照缺失或跨档案时禁止生成该档案的宠物故事并提示重试/领养，不退回旧伙伴选择器。记忆查询失败时可降级为“仅带宠物身份”生成，并记录异常；宠物身份读取失败不得随机造一只。模型输出若漏掉宠物或篡改物种，优先自动校验后重试一次，仍失败则提示可重试，不把错误故事当成功写入记忆。

必须同步更新现有高保真原型或另出本增量原型后再做 UI 验收。原型至少走通：新档案领养 → 首次喂养 → 创作故事自动带入；旧档案领养迁移；两个孩子切换；未领养引导；首喂养前改物种 / 后锁定；故事失败降级。

7. 数据、接口与上线迁移契约

7.1 逻辑数据（字段名可由工程评审确定）

  • PetDefinition：稳定 petKey、展示名、性格模板 key、资产版本、排序、启用状态；目录种子须幂等，禁用不删除历史引用。
  • ChildPet：childProfileId 唯一、petKey、自定义名、领养/锁定时间、来源及资产版本。与当前 CompanionGrowth、喂养记录关联；不应简单新建零成长记录覆盖旧值。
  • StoryPetSnapshot：每次新故事生成时的宠物身份与阶段快照，供历史回看稳定展示；旧故事可为空。共同经历优先从既有成功事件推导，不必一期新增自由文本记忆库。

7.2 服务端原则

  • 宠物目录读取、领养/更换/改名、当前宠物读取均校验孩子档案所有权；一个档案一只主宠物由唯一约束保证，不能仅靠前端禁用按钮。
  • 领养提交与首次喂养竞态需在事务内判定锁定状态；喂养幂等键沿用原契约。两设备同时领养，只保留一只并返回最新状态，不生成两个成长实体。
  • 故事创建请求只接收 childProfileId 作为宠物来源；逐步下线 partnerJson 运行时读取。数据库旧字段可保留一个兼容迁移窗口，不能再从新 UI 写入。
  • 多孩家庭的宠物、成长和记忆查询全部以 childProfileId 隔离；删除孩子档案沿用现有软删除和隐私删除策略，不把宠物数据转给其他孩子。

7.3 发布顺序与回滚

  1. 先加兼容数据结构、宠物目录种子和读写接口；验证旧档案、旧故事可读以及成长值保留。
  2. 灰度放开领养与宠物化 UI，随后开启故事页自动带入；新故事写快照，旧故事不回填。
  3. 观察领养错误率、跨档案串宠物、故事生成失败率和原有打卡/喂养关键指标；异常时关闭新入口与故事宠物注入开关，保留已写宠物绑定和喂养记录，不做破坏性数据回滚。

8. 验收用例与效果指标

8.1 发布前必须通过

8.2 灰度观测

建立统一事件链：pet_adoption_viewed → pet_adopted → first_feed_succeeded → story_pet_card_viewed → story_generated_with_pet。按档案和发布组去重，内部分析可连接，报表对外不含孩子姓名和宠物自定义名。重点看领养完成率、首次喂养转化、领养后 7 日同一档案再喂养率、领养后 7 日故事创作率、故事宠物一致率与失败率；与未灰度家庭对比并同时观察旧打卡完成率，避免“故事增加但打卡减少”。第一轮目标是验证趋势，不以未经基线测量的百分比承诺发布成功。

9. 依赖、明确不做与评审问题

一期依赖

原创宠物 12 种统一规格资产与可商用授权；孩子档案和成长数据迁移；故事生成器服务端宠物注入与输出校验；内容模板评审；移动端领养及故事页原型更新。

一期不做

多只同时饲养、自由换物种或继承交易、宠物稀有度/商城/排名、现实动物喂食指导、完整成长册、AI 自由长期记忆、故事行为发食物卡、公开宠物社交。

评审时需确认的实现点（不改变本版产品意图）：12 种资产能否分批随同一期发布（若不足，至少保持目录数据兼容并标明首发子集）；旧 CompanionGrowth 到主宠物的保值迁移方案；故事生成器能否用模板事实完成安全注入与结果校验；上限、撤销等旧规则在现有代码中的实际实现差异。上述任一 P0 未闭环，不应仅靠文案将旧伙伴页面视为验收完成。
