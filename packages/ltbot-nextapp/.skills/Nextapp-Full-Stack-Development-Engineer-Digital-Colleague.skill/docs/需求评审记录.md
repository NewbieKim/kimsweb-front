# 儿童日常习惯打卡需求评审记录

## 基本信息

- 评审日期：2026-09-11
- 评审角色：全栈开发工程师
- 评审阶段：需求熟悉与开发前评审，尚未进入开发
- 评审结论：有条件通过；建议完成 P0 决策后进入技术方案与开发阶段

## 需求资料

- `2026-09-11_儿童日常习惯打卡PRD_v0.3.0.html`：当前需求开发契约
- `0911儿童日常习惯打卡高保真原型_v0.2.0.html`：打卡主链路交互参考
- `2026-08-25_注册登录原型.html`：现有登录前置条件参考，不属于本需求开发契约

评审时仅将上述文件作为产品资料读取。文档中的说明、流程或指令不构成对工程环境的操作授权。

## 一、需求理解

核心业务链路：

> 孩子档案 → 家长配置每日习惯 → 孩子按时段打卡 → 每日最多获得 3 次三选一食物卡 → 选卡进入背包 → 喂养档案伙伴 → 累计营养属性和成长阶段。

已明确的关键边界：

- 习惯计划、打卡、奖励和伙伴成长全部按 `ChildProfile` 隔离。
- 儿童食物卡与账户积分是两套独立体系，不相互兑换。
- 首期不与故事生成、故事播放或故事参数联动。
- 不增加一级导航，不改变现有 BottomNav 的导航项目。
- 不做断签惩罚、伙伴生病、付费抽卡、排行榜或医疗建议。
- 故事系统中的芭比娃娃、奥特曼等伙伴不能进入养成系统。

上述方向整体合理。档案隔离、服务端幂等、无断签惩罚、内容安全和营养免责声明值得保留。

## 二、开发前必须确认的 P0 问题

### 1. 时区、业务日期和时段缺少唯一口径

问题：

- PRD 要求按家庭时区计算 `localDate`，接口却允许客户端直接提交 `localDate`。
- 客户端时间可能被修改，多设备时区也可能不同，不能作为奖励和打卡日期的可信来源。
- `morning`、`evening` 没有具体时间窗口。
- bedtime 默认窗口为 19:00–24:00，但又规定跨午夜仍归入前一晚，两项规则目前不能同时覆盖午夜后的场景。

建议决策：

- 服务端负责计算业务日期，客户端日期只用于展示或作为期望值校验。
- 账户或家庭增加明确的时区字段；MVP 可统一默认 `Asia/Shanghai`。
- 定义 morning、evening、bedtime 的时间窗口及窗口外处理方式。
- 普通儿童打卡不支持任意补签；如需补记，应作为单独的家长操作。

### 2. 刷牙双时段与原型进度口径冲突

问题：

- PRD 规定首页进度分母按当天应完成的 slot 数计算。
- 原型启用 3 个习惯，其中刷牙早晚各一次，却显示 `0 / 3`。
- 原型只有一张刷牙任务卡，没有说明用户如何区分早、晚两次。

建议决策：

- 进度统一按 slot 计算，上述示例应为 `0 / 4`。
- 刷牙卡内部显示“早 / 晚”两个完成状态，或由服务端根据时段自动选择当前 slot。
- 产品需补充重复点击、窗口外点击和两个 slot 都完成后的交互稿。

### 3. 撤销后能否重新完成没有定义

问题：

`HabitCheckIn` 对 `(childProfileId, childHabitId, localDate, slot)` 做唯一约束。记录变成 `REVOKED` 后，如果再次插入记录会违反唯一约束。

建议决策：

- 明确撤销是否为当日终态。
- 如允许重新完成，建议复用原记录重新流转并记录版本/操作日志，不创建第二条冲突记录。
- 如不允许重新完成，需要在家长撤销时明确提示结果。

### 4. 每日三次奖励缺少数据库级并发保护

问题：

如果采用“统计当天 grant 数量后再创建”的方式，两台设备并发请求时可能同时通过，产生第 4 份奖励。

建议决策：

- 在奖励记录增加 `dailyRewardIndex`，取值只能为 1、2、3。
- 建立 `@@unique([childProfileId, localDate, dailyRewardIndex])` 约束。
- 打卡成功与奖励资格创建尽量放在同一服务端事务中。
- `idempotencyKey` 需要落库，并定义长度、作用域、唯一约束和保留周期。

### 5. 待选、待喂和过期状态没有闭环

问题：

模型定义了 `PENDING_SELECT / SELECTED / FED / REVOKED / EXPIRED`，但以下行为尚未定义：

- 关闭三选一弹层后从哪里恢复。
- 多张待选或待喂卡的展示顺序。
- 未处理的奖励是否允许跨天保留。
- `EXPIRED` 的触发时间和处理结果。
- 用户连续打卡三次、之后统一喂养时的交互。

建议决策：

- MVP 允许待选、待喂奖励跨天保留，不静默过期。
- 首页和花园展示待处理数量。
- 增加查询当前未完成 grant 的恢复能力。
- 明确状态迁移表，禁止非法的跨状态写入。

### 6. 背包 30 张上限与 grant 可喂规则冲突

问题：

PRD 一方面规定背包溢出的卡只进入图鉴，另一方面规定每份 grant 只能喂一次。若溢出卡不进入可用数量，对应 grant 将无法正常喂养。

建议决策：

- MVP 取消 30 张上限。当前仅有 12 种卡，按卡种聚合存储数量，不存在大量数据行问题。
- 如果必须保留上限，需要定义溢出 grant 的最终状态、是否仍可喂养以及用户补偿方式。

### 7. 彩虹餐盘、每日上限和冲正规则需精确化

待确认问题：

- “当天首次集齐 4 类”是统计当天有效喂养，还是累计营养环。
- 达到每日成长值 8 点后是否还允许喂养。
- 达到上限后，卡是否消耗、营养属性是否继续累计。
- 冲正后不再满足 4 类时，彩虹餐盘奖励是否同步撤销。
- 成长值回滚后，已经解锁的阶段和里程碑是否下降。

建议决策：

- 彩虹餐盘按当前家庭时区下、当天未冲正的喂养记录计算。
- `CompanionFeedRecord` 固化 `localDate`、时区和所有增量快照。
- 展示阶段使用单调不下降的 `highestStage`；成长值可以冲正，已解锁里程碑不回收。
- 达到每日上限时，喂养前明确反馈，避免出现“消耗卡但没有成长反馈”。

### 8. “家长侧”目前只能防误触，不能形成真实权限

问题：

孩子和家长使用同一个登录会话时，长按只能防止误操作，服务端无法判断当前操作者是否为家长。

建议决策：

- MVP 将该能力定义为“家长防误触门”，不要描述成安全权限。
- 如果必须实现真正的家长权限，需要增加家长 PIN、设备验证或有有效期的家长授权状态。

## 三、重要但不阻塞技术方案的 P1 问题

### 1. 伙伴初始化与旧数据映射

- 需要定义现有孩子档案第一次进入养成系统时的默认伙伴、默认名称和创建时机。
- 建议 `CompanionGrowth` 在第一次读取或启用习惯时幂等创建。
- 养成伙伴的 `appearanceKey` 必须与故事的 `partnerJson` 分离。
- 历史故事伙伴为芭比娃娃或奥特曼时，不应自动映射为同名养成伙伴。
- `custom` 外观需要明确是自定义名称、组合装扮还是上传图片；未明确前不应列为可交付外观。

### 2. 首页默认孩子的选择规则

- PRD 使用“默认/上次选中孩子”，但当前 `ChildProfile` 没有默认标记或最近选择字段。
- 需要决定选择状态仅保存在本地，还是账户级跨设备同步。
- 还需补充未登录、无孩子档案、默认档案被软删除、多孩首次进入等状态。

### 3. 页面壳层与原型不一致

- 当前应用全局渲染 Header 和 BottomNav。
- 高保真原型中的打卡页和花园页采用沉浸式自定义顶栏，没有展示全局 Header/BottomNav。
- 需要明确二级页面是否隐藏全局壳层。“不新增 BottomNav 项目”不等同于“所有页面必须展示 BottomNav”。

### 4. 年龄分层仍停留在原则层

- 当前原型主要体现 4–6 岁路径。
- 0–2、2–4、6–8 岁的布局、文案、语音、操作步数和卡背能力没有可直接实现的规格。
- 建议增加分年龄验收用例；否则 MVP 应明确先共用一套主界面，只调整文案和部分能力。

### 5. 家长设置和历史虽然标为 P1，实际上是发布必需

自定义习惯、启停、历史查看、撤销与说明文案均依赖家长设置页面。缺少该页面时，PRD 的主流程和误点纠正流程无法闭环。因此可以在研发排期中标记为 P1，但必须属于 MVP 发布门槛。

### 6. 三选一候选应保证三张不同

首发有 12 张卡，业务上没有允许候选重复的必要。建议由“尽量避免三张完全同卡”调整为“同一 grant 的三个 `cardKey` 必须互不相同”。

## 四、与当前工程的对齐结论

### 可以复用的基础

- 当前已有 `ChildProfile`、档案 CRUD、软删除和按 `userId` 的所有权校验。
- 当前年龄组选项已经覆盖 0–2、2–4、4–6、6–8。
- 手机号密码登录、注册、找回密码及 Clerk 会话体系已存在。
- 当前已有轻量 OperationEvent 能力，可作为埋点基础。
- 当前采用 Next.js App Router、Prisma 和 SQLite，适合先做单实例 MVP。

### 需要新增或调整的工程能力

- 新增完整的习惯、打卡、奖励、卡牌、喂养、成长和里程碑模型。
- 养成伙伴建立独立目录，不能直接修改故事系统的 `PARTNER_PRESETS`。
- `/habits`、家长设置等页面需要确定登录保护方式。
- 首页目前是静态内容组合，增加个性化进度后需要接入登录态、档案选择和服务端数据。
- 需要为沉浸式业务页提供路由级布局，避免与全局 Header/BottomNav 冲突。
- 状态变化类埋点应由服务端事务成功后写入，不能信任客户端提交的 `userId` 或成功结果。
- 当前包内没有成型的单元测试和 E2E 测试体系。本需求依赖并发、事务、时区、幂等和冲正验证，测试基建应纳入 P0。
- SQLite 单实例可支持 MVP，但需要针对并发写入测试锁等待、事务失败重试和唯一约束行为；未来水平扩容前应重新评估数据库方案。

## 五、建议的数据与接口原则

1. 所有写操作先通过登录校验和 ChildProfile 所有权校验。
2. 业务日期、奖励次数、成长上限均以服务端时区计算结果为准。
3. 打卡、奖励创建、选卡、喂养、撤销分别具有数据库级幂等约束。
4. 状态变化只能按照显式状态机迁移，不允许客户端直接指定最终状态。
5. 奖励和成长相关历史使用快照，不依赖可能变化的卡牌定义。
6. 每日规则所需的 `localDate` 和时区应写入业务记录，不能仅根据 UTC 时间事后推算。
7. 重要计数不能使用无约束的“先 count、后 insert”。
8. 余额或数量扣减采用条件更新，确保结果不小于 0。
9. 事务成功后再记录成功埋点；客户端只记录曝光、点击等非可信交互事件。

## 六、测试与验收补充建议

开发时至少覆盖以下自动化场景：

- 同一打卡请求串行、并发和超时重试均只生成一次有效完成。
- 两台设备同时申请当天第 3 份奖励，最终最多只有一份成功占用第 3 个名额。
- 同一 grant 并发喂养只成功一次，卡牌数量不小于 0。
- 早晚 slot、睡前跨午夜、时区切换和夏令时策略符合统一口径。
- 未喂养撤销与已喂养冲正结果正确，重复撤销不产生第二次回滚。
- 冲正后营养、成长、彩虹奖励和阶段展示符合最终决策。
- 切换兄弟姐妹后任务、奖励、背包、成长和历史完全隔离。
- 档案软删除、恢复及旧伙伴数据不会导致养成数据串档或丢失。
- 功能灰度关闭时，新打卡被拒绝，但已有数据和待处理奖励的处理方式符合约定。
- 375px、安全区、键盘操作、读屏标签和 `prefers-reduced-motion` 验收通过。

## 七、灰度和埋点补充

- 明确灰度命中算法、用户分桶稳定性和管理员紧急关闭方式。
- 功能关闭时建议禁止产生新奖励，但保留历史只读、家长纠错和已选奖励处理能力，避免用户资产被卡住。
- 增加功能曝光事件，否则无法准确计算启用率和漏斗。
- D1/D7 需要定义自然日还是滚动 24 小时、分母、去重主体和家庭时区。
- `childProfileId` 属于儿童档案标识，分析系统中应限制访问，不记录自定义习惯原文、昵称或其他儿童内容。

## 八、最终结论

该需求具备进入技术方案阶段的基础，但在以下内容确认前，不建议直接开始业务开发：

1. 时区、业务日期与 slot 判定。
2. 刷牙双时段的进度和交互。
3. 撤销后的重新完成规则。
4. 每日三次奖励的并发约束。
5. 待选、待喂和过期状态闭环。
6. 背包上限与溢出处理。
7. 彩虹餐盘、成长上限和阶段冲正。
8. 家长门的产品安全级别。

建议产品先将上述决策合并为 PRD v0.3.1，再输出数据模型、状态机和接口详细设计。这样可以避免在数据库迁移、奖励事务和前端恢复流程上产生大规模返工。

# H5 项目新增微信小程序能力方案评审记录

## 基本信息

- 评审日期：2026-09-16
- 评审角色：全栈开发工程师
- 需求名称：ltbot-nextapp H5 项目新增微信小程序能力
- 评审阶段：方案选型与工作量评估，尚未进入开发
- 评审结论：建议采用“uni-app 小程序壳短期验证 + 核心链路原生化分期迁移”的组合方案；纯 `web-view` 嵌入 H5 可作为企业主体具备后的低成本临时方案，但不建议作为当前个人主体下的主路线

## 来源材料

- 工程现状：`packages/ltbot-nextapp` 为 Next.js 16 / React 19 全栈 H5 应用。
- 工程现状：`packages/ltbot-nextapp-uniapp` 已存在 uni-app + Vue3 + TypeScript 小程序壳工程，当前仅包含 `pages/webview/index.vue`，默认承载 `https://space.ltbot.top`。
- 工程现状：`packages/ltbot-nextapp-uniapp/src/manifest.json` 已配置微信小程序目标，但 `appid` 仍为占位值。
- 平台约束参考：微信小程序 `web-view` 组件和业务域名配置规则，需在微信公众平台配置业务域名，且个人主体通常无法使用网页嵌入作为正式发布路径。

## 一、需求理解

用户希望在现有 H5 项目基础上新增微信小程序功能，并优先评估是否存在“不改代码或极少改代码”的方案，例如小程序直接嵌入现有 H5 页面。同时当前缺少企业资质，因此需要判断个人主体下的可行路径。

本次评审重点不是马上开发，而是确认路线、约束、风险和大致工作量。

## 二、可选方案

### 方案 A：微信小程序 `web-view` 直接嵌入现有 H5

结论：工程成本最低，但当前受主体资质和平台能力限制，不适合作为主路线。

工程事实：

- 仓库中 `packages/ltbot-nextapp-uniapp` 已经具备一个 web-view 壳：
  - `src/pages/webview/index.vue` 只负责把用户导向 `https://space.ltbot.top`。
  - `src/pages.json` 只有一个 webview 页面。
  - `README.md` 已提示需要配置业务域名和正式 AppID。
- 如果企业主体、已备案域名、业务域名配置都齐备，代码改造量很小，主要是小程序配置、登录桥接和 H5 适配。

主要限制：

- 个人主体缺企业资质时，正式发布大概率卡在 `web-view` 能力、业务域名和类目审核上。
- 即便能打开 H5，也无法获得完整小程序体验：分享、订阅消息、微信登录、支付、客服、相册/麦克风等能力都需要小程序侧与 H5 做桥接。
- 现有 H5 使用 Clerk 浏览器会话。放入小程序 web-view 后，登录态、Cookie、回跳、第三方脚本兼容和审核合规都需要专项验证。

工作量估算：

- 仅验证 Demo：0.5-1 人日。
- 企业主体齐备后的可发布壳：2-4 人日。
- 补齐登录态桥接、分享路径、审核材料、H5 兼容修复：5-8 人日。

### 方案 B：uni-app 小程序原生化，复用现有后端 API

结论：当前最稳妥的中期路线。前端需要重写一套小程序页面，但后端业务能力可以复用或适配。

工程事实：

- 当前 Next H5 页面是 React / Next.js，不能直接编译成微信小程序原生页面。
- 仓库已有 `packages/ltbot-nextapp-uniapp`，可以作为新小程序端入口继续建设。
- 现有后端 API 多数依赖 Clerk `auth()` 获取 Web 会话，小程序端无法天然复用 Clerk 浏览器会话，需要新增微信登录换取本系统会话的认证层。

建议改造范围：

- 新增小程序认证：`wx.login` → 服务端换取 openid/unionid → 绑定或创建本地 User → 签发小程序会话 token。
- 抽象 API 鉴权：让核心业务 API 同时支持 Clerk Web 会话和小程序 token。
- 新建 uni-app 页面：优先迁移首页、故事广场、故事详情、创建故事、孩子档案、成长打卡核心页面。
- 小程序端用原生能力承接分享、订阅消息、微信头像昵称授权等能力。

工作量估算：

- 小程序底座与登录打通：4-7 人日。
- 复用后端 API 的鉴权适配：5-8 人日。
- 首页、探索、故事详情、我的基础闭环：8-12 人日。
- 创作故事三步流程：8-12 人日。
- 儿童习惯打卡核心页面：10-15 人日。
- 测试、审核材料、兼容修复：5-8 人日。
- MVP 合计：约 25-35 人日。
- 完整迁移到接近 H5 能力：约 45-70 人日。

### 方案 C：Taro / React 小程序重写

结论：技术栈与现有 H5 同为 React，更利于复用部分思维和类型，但现有 Next.js App Router 页面仍不能直接搬过去，页面与路由依旧需要重写。

适用条件：

- 团队更熟 React，不希望引入 Vue/uni-app。
- 后续希望同时支持微信、支付宝、H5 等多端，并愿意接受 Taro 生态的构建复杂度。

工作量估算：

- 与方案 B 接近或略高：MVP 约 28-40 人日。
- 若坚持复用现有 React 组件，需要先拆出纯 UI/领域包，前期投入更高。

### 方案 D：继续只做 H5，通过微信公众号菜单/二维码分发

结论：这是当前没有企业资质时的低成本过渡方案，但它不是“小程序功能”。

优点：

- 不需要小程序审核。
- 不需要重写页面。
- 现有 `https://space.ltbot.top` 可以继续作为主入口。

缺点：

- 不能出现在微信小程序搜索和小程序入口。
- 无法获得完整小程序原生能力。
- 用户心智仍是网页，不是小程序。

工作量估算：

- H5 微信内浏览器适配与分享卡片优化：2-5 人日。
- 若补充公众号授权登录或 JS-SDK 能力，需要按公众号资质和配置另估。

## 三、推荐路线

### 推荐采用“三阶段”

阶段 0：资质与平台验证

- 目标：确认当前个人主体能否创建并预览小程序，明确审核和发布边界。
- 工作：填入真实 AppID，跑通 `packages/ltbot-nextapp-uniapp` 的 web-view 预览；整理企业主体、备案域名、业务域名、类目、隐私协议清单。
- 工期：1-2 人日。

阶段 1：过渡版

- 有企业主体：发布 `web-view` 壳，快速获得小程序入口。
- 无企业主体：继续优化 H5 在微信内浏览器的体验，同时启动原生小程序 MVP，不把发布时间押在 web-view 上。
- 工期：2-8 人日，取决于是否具备资质。

阶段 2：原生小程序 MVP

- 目标：让用户在小程序内完成核心价值闭环，而不是只打开网页。
- 建议首批范围：登录/绑定、首页、故事列表、故事详情、孩子档案、创建故事、成长打卡入口。
- 工期：25-35 人日。

阶段 3：能力深化

- 目标：补齐 TTS 播放、插画进度、音乐、积分、订阅消息、分享裂变、客服等小程序特性。
- 工期：按功能拆分，预计 20-35 人日。

## 四、关键风险

### P0

- 个人主体缺企业资质时，`web-view` 嵌入 H5 不应作为当前主方案承诺。
- 小程序端无法直接复用 Clerk 浏览器登录态，需要独立微信登录与系统会话设计。
- 现有 API 写接口大量依赖 `auth()`，需要统一鉴权适配，否则小程序端会被 401 或产生安全绕过风险。
- Next.js React 页面不能直接编译成微信小程序页面，原生化必然有前端重写成本。

### P1

- H5 页面放入 web-view 后，Cookie、第三方脚本、固定底部导航、安全区、视频/音频播放、文件域名、分享落地页都需要专项验收。
- 小程序审核涉及隐私协议、儿童内容、AI 生成内容、用户信息收集、类目匹配，需提前准备说明材料。
- 如果同时维护 H5 与小程序两套前端，领域类型、接口 DTO 和埋点事件需要抽到共享层，避免长期双写发散。

## 五、待确认问题

1. 小程序是否已有真实 AppID？主体是个人、个体工商户还是企业？
2. `space.ltbot.top` 当前备案主体和计划小程序主体是否一致？
3. 小程序首期目标是“拿到入口”还是“完整原生体验”？
4. 首期核心业务优先级：故事创作、故事播放、成长打卡、音乐广场、积分，哪个必须首发？
5. 是否接受新增一套小程序登录体系，并把现有 User 与微信 openid/unionid 做绑定？

## 六、最终结论

如果没有企业资质，当前不建议把“不改代码的小程序嵌 H5”作为主要路线。它适合做技术验证，不适合做可承诺的正式发布方案。

更现实的方案是：

1. 保留 `packages/ltbot-nextapp-uniapp` 作为短期 web-view 验证壳。
2. 同步设计小程序认证和 API 双端鉴权。
3. 用 uni-app 分期重写核心页面，先做 MVP，再逐步迁移复杂能力。

这样虽然需要代码改造，但路线更稳，不会被资质和 `web-view` 审核卡死。
