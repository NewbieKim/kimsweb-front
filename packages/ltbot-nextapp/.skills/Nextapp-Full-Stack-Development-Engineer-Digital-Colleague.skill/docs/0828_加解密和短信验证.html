密码加解密与短信验证

用大白话把 ltbot-nextapp 注册 / 忘记密码这条链讲清楚：密码负责「路上别被人偷看」，短信负责「证明手机是你的」。登录页本身不走这套加密。

两件事各管什么

很多人一听「加密」和「验证码」容易混成一件事。它们解决的问题完全不同，代码也各管一段。

🔒

密码加解密

防止注册、重置时，明文密码出现在你们自己的 API 请求体里。用 RSA 公钥在浏览器锁上，服务端私钥打开，再交给 Clerk 存。

📱

短信验证

证明「这个人当时能收到这个号的短信」。通过后发一张 5 分钟、只能用一次的票（verifyToken），设密码必须带这张票。

🪪

真正存密码的地方

不是你们的数据库。解开后的明文交给 Clerk，Clerk 自己哈希存储。本地 User 表只记手机号、用户名，不存密码。

💡

类比：短信像小区门禁——先刷卡证明你住这儿；密码加密像把信放进只有银行能开的保险箱——快递员看不到内容。两张通行证都齐了，柜台才给办业务。

密码加解密

这不是「把密码加密后存库」。那是哈希，而且是 Clerk 的事。这里做的是传输加密：用户在浏览器里输入明文，提交到你们的 /api/auth/register 或 /api/auth/reset-password 之前，先用公钥锁上。

算法是 RSA-OAEP + SHA-256。公钥可以公开（打进前端包），只能锁箱子；私钥只放服务器，才能开箱子。中间的代理、日志、抓包看到的是一串 base64，打不开。

传输流程

对应代码

1. 浏览器加密

入口是 buildPasswordPayload。配了公钥就只提交密文字段；没配（本地开发）才退回明文，方便联调。

src/lib/password-crypto-client.ts ts 
export async function buildPasswordPayload(plain) {
  const encrypted = await encryptPassword(plain)
  if (encrypted) {
    return { passwordEncrypted: encrypted }  // 生产走这条
  }
  return { /* 明文兜底字段，仅本地未配公钥 */ }
}

// encryptPassword：
// 1. 读 NEXT_PUBLIC_AUTH_PASSWORD_PUBLIC_KEY_B64
// 2. Web Crypto 导入 RSA-OAEP / SHA-256 公钥
// 3. 加密后转 base64 再提交

注册页、忘记密码页提交前都会先调它：

src/app/(auth)/sign-up/[[...sign-up]]/page.tsx ts 
const payload = await buildPasswordPayload(plain)
await fetch('/api/auth/register', {
  method: 'POST',
  body: JSON.stringify({
    phone,
    verifyToken,   // 短信核过之后拿到的票
    ...payload     // passwordEncrypted 或明文兜底
  })
})

忘记密码页同理，只是打 /api/auth/reset-password。

2. 服务端解密

src/lib/password-crypto.ts ts 
// 从 AUTH_PASSWORD_PRIVATE_KEY_B64 还原 PEM
// 用 RSA_PKCS1_OAEP_PADDING + sha256 解密
// 得到 UTF-8 明文，再交给 Clerk

注册、重置接口的策略一样：

  • 带了 passwordEncrypted → 解密
  • 生产环境，或已经配了私钥，却没带密文 → 直接拒绝（防有人故意传明文）
  • 本地没配密钥 → 允许明文，方便开发
  • 解开后再校验规则：8–20 位，必须同时有字母和数字
✅

解开之后：注册走 Clerk createUser，重置走 updateUser。密钥用 node scripts/generate-password-key.mjs 生成。公钥进前端环境变量，私钥只进服务端。

登录为什么不加密

登录页把密码直接交给 Clerk 的 JS SDK（completeClerkSignIn），请求打到 Clerk，不经过你们的 API。路上是 Clerk 的 HTTPS，所以这套 RSA 用不上，也不应该在登录这条路上再绕一层。

⚠️

RSA 只管「经过我们自己接口的那一跳」。登录、Clerk Webhook、本地 User 表，都不是这套加密的职责。别把传输加密理解成「全站密码都加密了」。

短信验证

短信不负责设密码。它只证明：这个人当时能收到这个号的短信。验证通过后发一张票，后面设密码必须带票。

两个场景共用同一套代码，只是 scene 不同：

页面scene验证成功后
注册 register 去设密码并注册
忘记密码 forgot 去设新密码

整条链路（以注册为例）

对应代码

前端发码 / 核码

注册页 handleSendCode 打 POST /api/auth/send-code，body 带手机号和 scene: 'register'，按钮倒计时 60 秒。核码走 /api/auth/verify-code，成功后把返回的凭证存进页面状态，再切到设密码步骤。

忘记密码页几乎一样，只是 scene 换成 forgot。

发短信核心逻辑

src/lib/sms.ts · sendSmsCode ts 
// 1. 校验大陆 11 位手机号
// 2. 60 秒内发过 → 429
// 3. 当天已发 5 次 → 429
// 4. 写 SmsSendLog（手机号、场景、outId、ip）
// 5. mock：控制台打印固定码，不调阿里云
// 6. 生产：sendViaAliyun，有效 5 分钟、间隔 60 秒

阿里云实际发码在 sendViaAliyun，用服务端 AccessKey、短信签名、模板编号。验证码内容阿里云自己生成和保存。

核验接口

src/app/api/auth/verify-code/route.ts ts 
await verifySmsCode(phone, code, scene)           // 问阿里云 / mock 比对
const smsLogId = await markSmsVerified(...)       // 盖「已核验」章
createVerifyToken(phone, scene, smsLogId)         // 签发 5 分钟通行证

一次性通行证

票在 src/lib/auth/verify-token.ts。内容包括：手机号、场景、对应哪条短信日志、5 分钟后过期。再用 AUTH_VERIFY_SECRET 做 HMAC 签名，防止伪造。

注册 / 重置时 consumeVerifyToken 会检查：

  • 签名对不对、有没有过期
  • 手机号、场景是否对得上
  • 这条短信是否已经核验过（有 verifiedAt）
  • 是否已经用过（有 usedAt 就不能再用）

通过后立刻写上 usedAt，所以这张票只能用一次。验证码对了但注册失败（比如 Clerk 报错），票已经被撕掉，用户必须重新走短信。

SmsSendLog 字段含义
phone / scene发给谁、注册还是找回
outId阿里云流水号，核验时要对上同一笔
verifiedAt验证码核对通过的时间
usedAt票被注册 / 重置消费的时间

两件事怎么拼

注册和忘记密码都是「先证明手机，再设密码」：

flow 
短信通过  →  拿到 verifyToken
                     +
密码用公钥加密  →  passwordEncrypted
                     ↓
必须两样齐全，服务端才干活
🚫

没有有效票，光有加密密码也不行（证明不了手机是你的）。有票但生产环境密码没加密，也会被拒。两道门都要过。

开发与生产配置

本地可以少配东西；生产必须配齐。密钥和 AccessKey 的值一律脱敏，这里只列变量名。

变量放哪作用
NEXT_PUBLIC_AUTH_PASSWORD_PUBLIC_KEY_B64 前端 RSA 公钥，会打进浏览器包
AUTH_PASSWORD_PRIVATE_KEY_B64 仅服务端 RSA 私钥，解开密文
AUTH_VERIFY_SECRET 仅服务端 给短信凭证做 HMAC 签名，生产必须设强随机值
ALIBABA_ACCESS_KEY_ID / SECRET 仅服务端 阿里云号码认证
SMS_SIGN_NAME / SMS_TEMPLATE_CODE 仅服务端 短信签名与模板
SMS_MOCK_MODE 仅服务端 显式 true 走 mock；未配时非生产默认 mock，生产默认真实短信
🧪

本地默认：不配短信密钥 → 验证码固定为六位 123456。不配 RSA 密钥 → 密码可以明文提交。

生产必须：真实阿里云短信 + RSA 公私钥 + 凭证签名密钥。参考 env.production.example，真实值写在部署环境里，不要写进仓库。
