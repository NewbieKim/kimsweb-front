# 头脑风暴

## 何时使用

- 用户说“有什么方案”“帮我想想”“这个需求怎么做更好”。
- 产品需求不清晰，需要先扩展可能性再收敛。
- 技术方案有多个方向，需要比较成本、收益、风险。
- 需要和产品、后端、测试讨论前先形成结构化材料。

## 发散原则

- 先理解目标和约束，再提出方案。
- 不只给一个答案，至少覆盖保守方案、推荐方案和长期方案。
- 每个方案都说明适用场景、成本、风险和验证方式。
- 不为了炫技引入新框架或新依赖，优先沿用项目技术栈。
- 资金、权限、交易、导出、上传、协议等高风险链路优先稳定性。

## 思考维度

### 用户与业务

- 目标用户是谁，核心任务是什么。
- 当前流程痛点在哪里，是否影响主链路。
- 是否有角色、权限、状态、机构差异。

### 交互与页面

- 是新页面、改现有页面、弹窗、抽屉、步骤页还是详情页。
- 是否需要搜索、列表、汇总、分页、批量操作、导出。
- 是否存在空状态、错误态、只读态、禁用态。

### 技术实现

- 能否复用 `llsweb`、已有组件、全局能力和公共方法。
- 接口是否已有，是否需要后端新增字段或聚合接口。
- 是否需要 `pageCache`、keep-alive、路由参数加密。
- 是否涉及金额精度、分页、大数据量、重复提交。

### 协作与上线

- 是否需要功能开关、灰度、回滚方案。
- 是否依赖后端、产品、测试、运营配置。
- 是否需要补充埋点、文档或操作指引。

## 工作流程

1. 明确业务目标、约束条件和不可改变项。
2. 发散 2-4 个可行方案。
3. 从成本、风险、体验、扩展性和上线影响比较。
4. 推荐一个默认方案，并说明为什么。
5. 列出待确认问题和下一步动作。

## 输出模板

```markdown
## 背景理解

[目标、用户、约束]

## 可选方案

### 方案 A：[保守方案]

- 做法：[说明]
- 优点：[说明]
- 风险：[说明]
- 适合：[场景]

### 方案 B：[推荐方案]

- 做法：[说明]
- 优点：[说明]
- 风险：[说明]
- 适合：[场景]

### 方案 C：[长期方案]

- 做法：[说明]
- 优点：[说明]
- 风险：[说明]
- 适合：[场景]

## 推荐结论

[推荐哪个方案，以及取舍原因]

## 待确认问题

- [问题]

## 下一步

- [动作]
```

## 自检清单

- [ ] 是否先说明前提和约束。
- [ ] 是否至少给出 2 个方案并比较取舍。
- [ ] 是否避免引入不必要的新依赖或新架构。
- [ ] 是否覆盖产品、后端、测试和上线影响。
- [ ] 是否明确推荐方案和下一步。
