一、项目 Redis 使用概览

ltbot-server 是一个基于 Express + TypeScript 的轻量级后端服务， 引入 Redis 主要作为业务数据库和会话/消息存储使用， 而非仅做缓存层。核心场景包括：

📝 博客文章存储

使用 redis-om 提供的 Repository/Schema 抽象，对文章进行 CRUD 和搜索（Redis OM）。

📌 待办事项（Agency）

使用 Redis OM 存储代办事项，字段精简：title/description/status/priority。

💬 聊天会话与消息

使用原生 redis 客户端的 ZSET + Hash + List 组合，存储用户会话和消息流。

🛡️ 连接保护

中间件统一检查 Redis 是否就绪，未连接时返回 503，避免崩溃。

关键设计点：项目同时使用了 redis-om（高层抽象，依赖 RedisJSON+RediSearch） 和原生 redis（基础客户端）。前者用于文档型数据，后者用于需要精细控制 Key 与 TTL 的场景。

二、依赖与运行环境

来自 package.json：

"dependencies": {
  "dotenv": "^16.6.1",
  "express": "^5.1.0",
  "cors":   "^2.8.5",
  "redis":   "^5.10.0",     // 原生 Node.js Redis 客户端
  "redis-om": "^0.4.7"      // 对象映射库，需要 Redis Stack
}

运行环境

  • Node.js ≥ 20.0.0（ES Modules + top-level await 友好）
  • 推荐 redis/redis-stack（内置 RedisJSON 与 RediSearch）
  • 无 Redis Stack 时可使用普通 Redis，但 Redis OM 的全文搜索/索引能力会降级
⚠️ 生产环境必须：设置 bind、protected-mode、requirepass， 开放 6379 端口并配置防火墙（详见 [宝塔部署指南]）。

三、连接管理（db/redis.ts）

文件：db/redis.ts

本文件承担 4 个核心职责：

  1. 创建并配置 RedisClientType（含超时与重连策略）
  2. 定义两个 Schema（Article、Agency）
  3. 导出对应的 Repository 实例
  4. 提供 initRedis() 初始化函数（含索引创建 + ChatService 注入）

3.1 客户端配置

const redis: RedisClientType = createClient({
  url: 'redis://localhost:6379',     // 可通过 REDIS_URL 覆盖
  socket: {
    connectTimeout: 10000,            // 10s 连接超时
    reconnectStrategy: (retries) => {
      if (retries > 3) {
        console.error('❌ Redis 重连失败，已达最大重试次数')
        return new Error('Redis 连接失败')
      }
      console.log(`🔄 Redis 重连中... (${retries}/3)`)
      return Math.min(retries * 100, 3000) // 指数退避
    }
  }
})

redis.on('error',   (err) => console.log('Redis Client Error', err))
redis.on('connect', () => console.log('✅ Redis Client Connected'))

3.2 初始化流程 initRedis()

export const initRedis = async () => {
  if (!redis.isOpen) {
    await redis.connect()                        // 1. 建立连接
    // 2. 尝试创建 RediSearch 索引
    try { await articleRepository.createIndex()
          await agencyRepository.createIndex() }
    catch (e) { console.error('❌ 索引创建失败', e) }

    // 3. 注入 ChatService（使用同一个 redis client）
    try { initChatService(redis as any) }
    catch (e) { console.error('❌ ChatService 初始化失败', e) }
  }
}

说明：

  • 使用 isOpen 守卫，保证整个进程只 connect 一次。
  • 索引创建失败不会阻断服务启动——会降级运行（仅普通搜索可用）。
  • closeRedis() 提供优雅关闭入口。

七、聊天模块（db/chatService.ts）

文件： db/chatService.ts、 routes/chat.ts

本模块是项目里 Redis 用法最丰富的部分。放弃 Redis OM， 改用原生 redis 客户端，以便精细控制 Key 与 TTL。

7.1 三个 Key 的数据结构

Key类型用途
chat:user:{userId}:sessionsZSET用户的会话列表，score=timestamp
chat:session:{userId}:{sessionId}Hash会话元数据（id/title/lastMessage/...）
chat:messages:{userId}:{sessionId}List会话内的消息（JSON 字符串）

7.2 关键操作

// 创建会话
const sessionId = `chat-${Math.floor(Date.now()/1000)}`
await client.zAdd(`chat:user:${userId}:sessions`, { score: ts, value: sessionId })
await client.hSet(`chat:session:${userId}:${sessionId}`, { id, userId, title, ... })
await client.expire(sessionKey, 30 * 24 * 60 * 60)  // 30 天

// 拉取会话列表（分页 + 排序）
const total      = await client.zCard(key)
const sessionIds = sortBy === 'desc'
  ? await client.zRangeWithScores(key, start, end, { REV: true })
  : await client.zRangeWithScores(key, start, end)

// 保存消息
const messageStrings = messages.map(m => JSON.stringify(m))
await client.rPush(messagesKey, messageStrings)
await client.expire(messagesKey, 30 * 24 * 60 * 60)

// 删除会话（清理三项 Key）
await client.del(sessionKey, messagesKey)
await client.zRem(userSessionsKey, sessionId)

八、连接检查中间件

为避免 Redis 未连接时崩溃，所有使用 Redis 的路由都加了统一守卫：

// article / agency 路由
const checkRedisConnection = (req, res, next) => {
  const client = (articleRepository as any).client
  if (!client || !client.isOpen) {
    return res.status(503).json({
      success: false,
      message: 'Redis 服务未连接，文章功能暂时不可用',
      tip:    '请启动 Redis 服务：docker run -d -p 6379:6379 redis/redis-stack:latest'
    })
  }
  next()
}
router.use(checkRedisConnection)

// chat 路由
const checkRedisConnection = (req, res, next) => {
  try { getChatService(); next() }   // 未初始化时抛错
  catch {
    return res.status(503).json({
      success: false, message: 'Chat 服务未初始化或 Redis 未连接',
      tip: '请启动 Redis 服务'
    })
  }
}

这种 "Fail Fast + 503 + 修复提示" 模式能显著降低运维成本。

九、Redis Key 设计

项目使用了清晰的命名空间与分层 Key 模式：

模块Key 模式类型TTL
Articlearticle:<entityId>JSON（Redis OM）永久
Agencyagency:<entityId>JSON（Redis OM）永久
Chat 会话列表chat:user:{userId}:sessionsZSET30 天
Chat 会话chat:session:{userId}:{sessionId}Hash30 天
Chat 消息chat:messages:{userId}:{sessionId}List30 天

设计原则

  • 冒号分层：业务域:实体:属性，便于 KEYS chat:* 运维排查。
  • 用户隔离：会话 Key 包含 userId，天然避免跨用户访问。
  • 30 天 TTL：聊天场景对历史依赖较低，使用过期清理降低内存压力。
  • 业务数据不设 TTL：文章和待办属于业务数据，无显式过期。

十、部署与运维

项目内置了完整的部署文档： 宝塔Redis远程配置指南.md。

关键点速查

  • bind：本地 127.0.0.1；远程 0.0.0.0 或固定 IP。
  • protected-mode：仅在 bind 非本机时设为 no。
  • requirepass：远程访问必须设置 ≥ 16 位强密码。
  • maxmemory + maxmemory-policy：建议 allkeys-lru。
  • 端口：默认 6379；生产建议改为非常规端口（如 16379）。
  • 云安全组：阿里云/腾讯云/AWS 都要放行 6379/TCP。
  • 持久化：开启 RDB（或 AOF），防止重启数据丢失。

十一、Redis 知识补充

本节结合 Redis 官方文档与社区资料，补充 ltbot-server 未直接用到、但 Redis 全景中重要的知识点。

11.1 五大基础数据类型

类型底层特点典型场景
StringSDS最大 512MB，原子自增缓存、计数器、分布式锁
Hashziplist（小）/ hashtable（大）字段可独立更新用户/商品对象
Listquicklist（双向链表 + ziplist）有序可两端 push/pop消息队列、最新列表
Setintset / hashtable无序、唯一、交并差标签、共同关注
Sorted Set跳表 + 哈希按 score 排序排行榜、滑动窗口限流

11.2 高级类型

  • Bitmap：位操作，适合签到、活跃统计（1 亿用户 ≈ 12MB）。
  • HyperLogLog：基数统计，固定 12KB，误差 < 1%，适合 UV。
  • GEO：基于 ZSet + Geohash，GEOADD / GEOSEARCH 查附近。
  • Stream：5.0+ 的消息流，XADD/XREADGROUP/XACK，支持消费组。

11.3 Redis OM 是什么

Redis OM（Object Mapping）是 Redis 官方推出的高级抽象库，特性：

  • 通过 Schema 声明字段类型（string / number / date / text / string[] / boolean / point）。
  • 提供 Repository 进行 save / fetch / remove / search。
  • 流式查询：search().where('field').equals(x).sortDescending('y').return.page(0,10)。
  • 依赖 RedisJSON + RediSearch（Redis Stack 内置），普通 Redis 仅有基础能力。

11.4 持久化机制

  • RDB（快照）：周期性全量 dump，save 触发。文件紧凑、恢复快，但可能丢数据。
  • AOF（追加日志）：每条写命令追加到文件，最多丢 1s。文件较大、可重写。
  • 混合持久化（Redis 4+）：RDB 全量 + AOF 增量，兼顾速度与安全。

11.5 常见运维命令

# 连接
redis-cli -h HOST -p 6379 -a PASSWORD

# 键管理
KEYS chat:*              # 匹配（生产慎用，会阻塞）
SCAN 0 MATCH chat:* COUNT 100
TTL chat:session:...     # 查看剩余过期时间
EXPIRE key 60            # 设置过期

# 监控
MONITOR                  # 实时命令流（调试用）
SLOWLOG GET 10           # 慢日志
INFO memory              # 内存使用

11.6 数据淘汰策略（maxmemory-policy）

策略行为
noeviction写满后报错（默认）
allkeys-lru所有 key 中淘汰最久未用 ⭐推荐
volatile-lru只淘汰设置了过期时间的
allkeys-lfu所有 key 中淘汰最不常用（Redis 4+）
volatile-ttl优先淘汰即将过期

11.7 典型坑点

  • 大 Key：单个 String > 10KB、Hash/List 元素 > 1 万，会导致阻塞与慢查询。
  • 热 Key：单 key 流量过大导致单分片瓶颈，可用 --hotkeys 发现。
  • 无密码 + bind 0.0.0.0：极易被挖矿。
  • KEYS 命令：O(N) 阻塞主线程，生产必须用 SCAN。
  • 无持久化：重启即丢数据；务必开启 RDB 或 AOF。

十二、最佳实践与注意事项

✅ 项目中已落地

  • 统一的 Redis 连接管理（redis.ts）
  • 连接状态检查中间件（503 + 修复提示）
  • 分层 Key 命名 + 用户维度隔离
  • 聊天数据 30 天 TTL 自动清理
  • 索引创建失败时降级运行
  • 完整的 TypeScript 类型 + 错误处理

⚠️ 仍可优化

  1. 批量操作 Pipeline：会话列表中 N 个 HGETALL 可合并为一次 pipeline，减少 RTT。
  2. 消息分页：当前一次性 LRANGE 0 -1，长会话应按页加载。
  3. JWT 鉴权：当前 getUserId 仅从 header 读取，生产需替换为真实身份。
  4. 请求限流：建议 express-rate-limit + Redis 计数。
  5. 参数校验：用 zod 做入参 schema 校验。
  6. 分布式锁：并发写同一会话时可用 SET NX + 唯一 ID 实现乐观锁。
  7. 监控告警：接入 SLOWLOG、INFO 指标到 Grafana / Sentry。
